# 04 · useEffect와 데이터 페칭

예상 시간: 60~90분 (두 세션으로 나눠도 됨) · 개념: `useEffect`, 의존성 배열, cleanup, 로딩·에러·성공 상태 모델링, 경쟁 상태, 이펙트가 필요 없는 경우, StrictMode의 이중 실행

지금까지는 데이터가 처음부터 코드 안에 있었습니다. 이번에는 **화면이 뜬 뒤에 도착하는** 데이터를 다룹니다. 그러면 "아직 안 왔다", "오다가 실패했다", "왔는데 이미 낡았다" 같은 상태가 새로 생깁니다.

## 목표

도서 검색 화면. 처음 뜰 때 전체 목록을 불러오고, 검색어를 입력하면 그 검색어로 다시 불러옵니다.

## 시작 마크업과 API

- `src/starters/Starter04.jsx` — 정적 화면. **http://localhost:5173/?starter=04**
- `src/data/books.js` — 책 14권. `{ id, title, author, year, tags }`
- `src/api/booksApi.js` — **가짜 API. 수정하지 마세요.**

```js
import { fetchBooks } from './api/booksApi'

fetchBooks('리액트')                    // Promise<Book[]>
fetchBooks('리액트', { signal })        // AbortController의 signal (선택)
```

가짜 API에는 실습을 위한 규칙이 두 개 있습니다.

1. **검색어가 짧을수록 응답이 느리게 옵니다.** (`""` → 1400ms, `자` → 1200ms, `자바스크립트` → 200ms)
2. **검색어에 `에러`가 들어가면 실패합니다.** 에러 화면과 `다시 시도`를 확인할 때 쓰세요.

요청·응답·취소를 콘솔에 `[api]`로 찍습니다. 일부러 찍는 로그이니 지우려 하지 마세요 — 이번 실습에서 무슨 일이 일어나는지 보는 창구입니다.

`App.jsx`는 이번 실습 화면으로 교체합니다. 03 컴포넌트는 `src/components/exercises/03/`에 그대로 두고 참조만 끊으면 됩니다. 새로 만드는 컴포넌트는 `src/components/exercises/04/`에, 태그 배지는 `src/components/ui/Badge`를 **수정 없이** 재사용하세요.

## 이번에 쓰게 될 JS 문법

React 개념에 집중할 수 있게 문법은 먼저 정리해 둡니다.

**Promise와 `await`** — `fetchBooks(…)`는 "나중에 값이 도착할 것"을 나타내는 Promise를 돌려줍니다. `await`를 붙이면 도착할 때까지 그 줄에서 기다린 뒤 값을 꺼내 줍니다. `await`는 `async` 함수 안에서만 쓸 수 있습니다.

```js
async function load() {
  try {
    const result = await fetchBooks('리액트')   // 성공하면 배열
    console.log(result)
  } catch (err) {
    console.log(err.message)                    // 실패하면 여기로
  } finally {
    console.log('성공이든 실패든 마지막에 한 번')
  }
}
```

`await` 없이 쓰면 이렇게 됩니다. 위와 같은 뜻입니다.

```js
fetchBooks('리액트')
  .then((result) => console.log(result))
  .catch((err) => console.log(err.message))
```

**중요**: `await`로 기다리는 동안 그 함수는 멈춰 있지만 **화면은 멈추지 않습니다.** 그 사이 사용자가 또 타이핑을 하고 컴포넌트가 다시 렌더될 수 있습니다. 그래서 `await` 다음 줄은 "한참 뒤의 세상"에서 실행됩니다 — 03에서 이야기한 스냅샷이 여기서 다시 나옵니다.

**`AbortController`** — 진행 중인 요청을 취소하는 표준 도구입니다.

```js
const controller = new AbortController()
fetchBooks('리액트', { signal: controller.signal })
controller.abort()   // 취소 → 그 Promise는 name이 'AbortError'인 에러로 실패한다
```

취소된 요청은 에러로 떨어지므로, 그걸 "진짜 에러"와 구분해야 합니다. `err.name === 'AbortError'`로 판별합니다.

**정렬** — `sort`는 **원본 배열을 직접 바꿉니다.** state로 받은 배열에 그냥 쓰면 03에서 지킨 불변성이 깨집니다. 복사한 뒤 정렬하세요. 한글 가나다순은 `localeCompare`입니다.

```js
const sorted = [...books].sort((a, b) => a.title.localeCompare(b.title))
```

**`?.`** — `signal?.aborted`는 `signal`이 있을 때만 `.aborted`를 읽습니다. 값이 없을 수 있는 자리에만 쓰세요. 원인을 모르는 에러를 덮는 데 쓰면 01에서처럼 버그가 숨습니다.

## 요구사항

### 목록 불러오기

1. 화면이 처음 뜨면 `fetchBooks("")`로 전체 목록을 불러옵니다. 이 호출은 버튼 클릭 같은 이벤트가 아니라 **화면이 나타났다는 사실** 때문에 일어납니다 — 이펙트가 필요한 경우입니다.
2. 요청 중에는 `loading` 스피너만, 성공하면 목록만, 실패하면 `alert alert-error` + `다시 시도` 버튼만 보입니다. **동시에 두 개가 보이면 안 됩니다.**
3. 성공했지만 결과가 0권이면 목록 대신 `empty` 상자가 나옵니다.
4. 헤더 오른쪽 `N권`은 결과 개수입니다.

### 검색

5. 검색 입력은 제어 컴포넌트입니다. **입력이 바뀔 때마다** 그 검색어로 다시 요청합니다. (디바운스는 넣지 마세요. 요구 7에서 필요합니다.)
6. `다시 시도`는 지금 검색어로 같은 요청을 다시 보냅니다.

### 경쟁 상태

7. 아래 **실험**에서 확인한 문제를 이펙트의 **cleanup**으로 해결합니다. 방법이 두 가지 있습니다. 하나를 고르고 이유를 답하세요.
   - (a) "이 요청은 이미 낡았다"고 표시해 두고, 늦게 도착한 응답을 무시한다
   - (b) `AbortController`로 낡은 요청 자체를 취소한다

### 정렬

8. 결과를 **제목 가나다순**으로 정렬해서 보여줍니다.

### 실험 (하나뿐입니다. 꼭 하세요)

9. 요구 7을 만들기 **전에** 확인합니다. 검색창에 `자`를 치고 곧바로 이어서 `자바스크립트`까지 입력하세요.
   - **예측을 먼저 적으세요**: 입력이 끝나고 잠시 뒤, 화면에 남는 목록은 어느 검색어의 결과일까요?
   - 실행하고 콘솔의 `[api]` 로그로 요청과 응답의 순서를 확인하세요.
   - 결과를 적어 두고 요구 7로 넘어갑니다.

## 완성 조건

각 항목에 확인 방법을 적어 뒀습니다. **브라우저에서 그대로 해 보고** 체크하세요. 못 한 항목은 비워 두고 보고하면 됩니다.

- [ ] 첫 화면에서 목록이 자동으로 불러와진다 — *확인: 새로고침 → 스피너가 잠깐 보이고 14권이 나온다*
- [ ] 로딩·에러·목록·빈 결과가 서로 겹치지 않는다 — *확인: `에러` 입력 → 에러 화면만, `zzz` 입력 → `empty`만, 지우면 목록만*
- [ ] `다시 시도`가 지금 검색어로 다시 요청한다 — *확인: 에러 화면에서 버튼을 누르면 콘솔에 `[api] 요청 시작`이 한 줄 더 찍힌다*
- [ ] 입력이 바뀔 때마다 재요청된다 — *확인: 한 글자씩 칠 때마다 `[api] 요청 시작`이 한 줄씩*
- [ ] 경쟁 상태가 해결됐다 — *확인: 실험 9를 다시 하면 화면에 **마지막에 입력한** 검색어의 결과가 남는다*
- [ ] 이펙트가 cleanup 함수를 돌려준다 — *확인: `useEffect` 콜백 안에 `return () => {…}`이 있다*
- [ ] 정렬된 배열을 담는 `useState`와 그것을 채우는 `useEffect`가 없다 — *확인: 정렬은 렌더 중에 계산된다. `sort`를 쓴 곳에서 원본을 복사했는지도 같이 확인*
- [ ] `N권`이 결과 개수와 맞는다 — *확인: `zzz` 검색 시 `0권`*
- [ ] `npm run lint` 경고 없음, 콘솔에 React 경고·에러 없음 — *확인: `[api]` 로그는 가짜 API가 일부러 찍는 것이니 무시*
- [ ] 스타터에 없는 태그 · className · CSS를 새로 만들지 않았다 — *확인: `ui/Badge`는 수정하지 않고 그대로 사용*

1. `useEffect`의 의존성 배열에 무엇을 넣었나요? 거기에 ① 빈 배열 `[]`을 넣으면 ② 검색어를 넣으면 ③ 배열 자체를 생략하면 각각 언제 이펙트가 실행되나요? ③은 실제로 해 보면 바로 알 수 있습니다.
2. 실험 9에서 **늦게 도착한 옛 응답이 화면을 덮은** 이유를 설명해 보세요. `await`(또는 `.then`) **다음 줄**이 실행되는 시점과, 그 줄이 보고 있는 검색어가 어느 렌더의 값인지를 중심으로요. 03에서 `setTodos([...todos, x])`를 세 번 호출했을 때와 무엇이 같습니까?
3. 요구 7에서 (a)와 (b) 중 무엇을 골랐고 왜 그랬나요? 고르지 않은 쪽의 단점은 무엇입니까? 그리고 cleanup 함수는 **언제** 불립니까?
4. 요구 8의 정렬을 `useState` + `useEffect`로("결과가 바뀌면 이펙트에서 정렬해 다른 state에 담는다") 만들면 어떤 문제가 생기나요? "이 일은 이펙트로 할 일이 아니다"를 판단하는 기준을 한 줄로 적어 보세요.
5. 콘솔을 보면 첫 요청이 **두 번** 나갑니다. 개발 모드의 `StrictMode`가 이펙트를 일부러 두 번 실행하기 때문입니다. React는 왜 이런 짓을 할까요? 이걸로 잡아내려는 버그가 무엇일지 생각해 보세요. (요구 7을 제대로 만들었다면 두 번 실행돼도 화면은 멀쩡합니다.)
