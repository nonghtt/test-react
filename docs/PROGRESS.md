### 03 상태 끌어올리기 · 할 일 목록 — ✅ 보완 후 통과 (2026-09-21)

  - `setX(prev => …)` vs `setX(값)`: `아침 루틴 추가` 버튼이 **1개 추가 함수를 3번 호출**하도록 요구사항에 명시(요구 4) → 직접 값 형태면 1개만 추가되는 것을 직접 보게 함(실험 12a/12b). 완성 조건에 "한 번 누르면 3개 늘어난다"를 넣어 우회 불가.
  - state는 스냅샷: 세 호출 사이에 `console.log(todos.length)`(실험 12c) → 같은 값 세 번을 근거로 질문 1·2를 본인 문장으로 답하게 함. 02에서는 설명을 들었던 부분.
  - 끌어올리기: 입력 폼·필터 탭·목록·항목 한 줄을 **서로 다른 파일**로 강제(요구 1). 필터 state는 탭과 목록 둘 다 필요 → 부모로 올라가야 함. 탭 옆 개수·`N개 중 M개 완료`·빈 상태 문구는 파생 값. 헤더 버튼과 입력 폼 두 곳이 추가 기능을 필요로 함.
  - 반대 방향도 한 번: 편집 중 입력값은 **아래에 남는** state, "편집 중인 항목 id"는 올라가는 state(요구 11, 질문 5).
  - 출제 당시에는 0단계(코딩 전 설계 쓰기)를 포함했으나, 같은 날 사용자 결정으로 **폐지하고 실습 파일에서 제거**했다. state 위치 판단은 요구 1·11과 질문 4·5로만 확인한다.
  - 완성 조건 자가 대조를 문단으로 명시("못 한 항목은 비워 두고 보고하면 된다").

#### 진행 과정 (2026-09-21, 하루에 출제·구현·리뷰까지)

- **편집 state 설계에서 세 번 왕복**: 줄마다 `isEditInputVisible` boolean → `[{ id, editMode }]` 배열(todos와 id를 복사) → `editInputId` 하나. 마지막으로 넘어간 계기는 "`Tab`에서는 탭마다 `{ id, active }`를 두지 않고 `activeTabId` 하나로 풀었다"는 비교. 본인이 세운 규칙("하나만 true, 나머지 전부 false")이 곧 "정보는 id 하나"라는 뜻임을 짚자 스스로 정리.
- **필터 방식을 두 안으로 정리해 스스로 물어 옴**: ① 탭이 바뀔 때 `todos`를 갈아치운다 ② `activeTabId`를 내려보내 걸러낸다. 질문으로 ①이 원본을 잃는다는 점과 걸러낸 목록이 파생 값이라는 점을 확인 → ②로 결정.
- **JS 문법이 병목**: 화살표 함수 블록 본문의 `return` 누락과 `map`/`filter` 혼동이 연속으로 나왔다(삭제에 `map` + boolean 반환 / `onEditBtn`의 `if` 블록에 `return` 누락 / `useState` 초기값의 `(todo) => { ({…}); }` / `tabs.filter(...).status`). 사용자가 **"규칙을 설명하지 않고 횟수만 센다"고 지적** — 타당한 지적이었다. 표현식 본문 vs 블록 본문, `=> ({…})`의 괄호, `map`/`filter`/`find`의 차이를 정리해 설명한 뒤로는 재발하지 않았고 `find`도 스스로 적용했다.
- **"우연히 동작하는 코드"를 설명하게 함**: `editInputId` 초기값이 배열인데 화면이 정상으로 보였던 이유(`===`는 타입 변환을 하지 않아 항상 `false`, 그게 "아무것도 편집 중 아님"과 화면상 동일)를 따라가게 했다.
